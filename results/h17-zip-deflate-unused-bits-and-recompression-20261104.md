# Original archive ZIP: DEFLATE stream reconstruction and unused-bit census

**Agent27, 4 November 2026 00:01 UTC.** Distinct source-carrier test motivated by K04's missing 128-bit coupon. The original 50,526-byte user-supplied H17 ZIP holds **46 DEFLATE-compressed regular file members**. This study asks whether the byte streams themselves can contain information **independent of their extracted files** through ignored final-byte bits or nonstandard compression choices. Earlier ZIP raw-byte window scans did not decode the ignored individual end bits or reproduce entire compressed streams from the extracted evidence.

Original ZIP SHA256 `e778552c555fac652e24fd09e1c4f31bd066b4686e624b91f6e94e1d64342bf7` was verified. For each member, read its compressed stream from the original local ZIP header, independently decode raw DEFLATE to match the original CRC-checked member, and recompress the same decompressed bytes with installed **zlib 1.3.1, level 6, default strategy, raw DEFLATE**. All **46 of 46 compressed bytestrings match their independently regenerated bytestrings exactly**. This comparison covers **entire compressed streams**, not just their contents, sizes or checksums. Version dependence is possible; the exact result is observed for zlib 1.3.1.

For each member's last compressed byte, exhaust every altered value of its uppermost 1..7 bits, retaining an altered prefix size only when **every** replacement produces byte-identical decompression. This identifies otherwise ignored trailing payload capacity without interpreting Huffman code tables. Across all 46 members, the determined end-of-stream ignored-bit capacities have histogram:

**All 170 original ignored bits are zero.** The spare terminal bit capacity would nominally suffice for an independent 128-bit field, but contains no such nonzero data in this ZIP. Combined with exact byte-for-byte default-zlib reproduction, this rules out a separately encoded coupon *in that particular terminal-bit channel* and provides strong evidence that the compressed bytes are ordinary packaging output rather than a custom-compressed secondary message. It does not mathematically exclude an arbitrary deliberately hidden code embedded in the extracted plaintext itself, filenames, outer ZIP ordering, or other channels.
